# 代理节点功能优化实施计划

> 文档状态：实施基线  
> 制定日期：2026-08-20  
> 适用代码基线：当前 `main` 工作区最终代码  
> 核心版本：sing-box 1.13.15（继续使用 `resources/core/manifest.json` 锁定版本与哈希）

## 1. 目标与范围

本计划用于扩展 WinRouter 的代理节点功能，使用户可以在代理页面管理、测试并选择代理节点，同时明确代理服务器连接使用的物理出口。目标协议为 HTTP CONNECT、Shadowsocks、VMess、VLESS 和 Trojan，并逐步支持常见订阅链接。

本次优化必须保持现有双出口直连、规则顺序、DNS 隔离、IPv6 策略、恢复机制和 helper 安全边界不变。所有代理配置仍由 Go 后端生成，不允许前端或订阅直接提交任意 sing-box JSON。

### 1.1 本期目标

1. 建立可扩展、强类型、可迁移的代理节点模型。
2. 支持手工添加 VMess、VLESS、Trojan 节点，保留 HTTP CONNECT 和 Shadowsocks。
3. 支持为代理节点选择物理出口 A 或 B，默认使用出口 B。
4. 支持协议级连通性测试，而不是仅测试服务器端口是否可连接。
5. 支持 `ss://`、`vmess://`、`vless://`、`trojan://` 分享链接及 Base64 多行订阅。
6. 在后续阶段支持常见 Clash/Mihomo YAML 订阅的受限子集。
7. 保持订阅原子更新、凭据 DPAPI 加密、代理防环路和失败不直连回退。

### 1.2 暂不纳入

- 不接受任意 sing-box、Clash 或 Xray 完整配置。
- 不实现自动选择最快节点、故障时自动切换节点或负载均衡。
- 不在首期支持 Reality、ECH、Hysteria2、TUIC、WireGuard、SSH 等协议。
- 不在首期实现订阅定时后台刷新。
- 不改变现有规则编辑器和双端口直连分流的匹配语义。

Reality、Hysteria2 和 TUIC 可在 VMess/VLESS/Trojan 稳定后单独评估。Reality 会增加公钥、short ID、指纹等字段，Hysteria2/TUIC 还涉及 UDP、拥塞控制和测速语义，不应与第一批协议混合实施。

## 2. 当前代码基线

当前实现已经具备一条完整但协议范围有限的链路：

- `internal/nodes` 保存节点、选择状态和收藏，节点 Schema 为 2。
- 节点密码和订阅 URL 使用当前 Windows 用户的 DPAPI 加密。
- 节点类型仅允许 `http` 和 `shadowsocks`。
- `internal/subscriptions` 支持受限版本 1 JSON，以及 Base64 编码的 `ss://` 列表。
- HTTP 节点使用 CONNECT 做健康检查，其他节点仅做 TCP 建连。
- `internal/config.MVPProxy` 和 `config.Outbound` 只包含 HTTP/SS 所需字段。
- 代理模式固定将代理 outbound 绑定到接口 B，并生成代理服务器 `/32 -> foreign-direct` 防环路规则。
- 前端保存一个全局所选节点；应用配置时由 `App.withSelectedProxy` 解密凭据、解析节点域名并注入配置。
- 域名节点当前要求全局 DNS 为固定 UDP 53，并从接口 B 的源 IPv4 发起解析。

现有实现中，`Username` 在 Shadowsocks 节点上被复用为加密方法。这种复用不能继续扩展到 VMess、VLESS 和 Trojan。

## 3. 核心设计决策

### 3.1 分离代理节点与物理出口

以下两个概念必须独立：

- 代理节点：远端 HTTP/SS/VMess/VLESS/Trojan 服务。
- 物理出口：WinRouter 连接远端代理服务器时使用的接口 A 或 B。

节点模型新增 `egress`，值只允许 `a` 或 `b`，默认 `b`。配置生成时根据该值选择 `InterfaceA.BindInterface` 或 `InterfaceB.BindInterface`，并将代理 endpoint 防环路规则路由到对应的 direct outbound。

首版不提供“自动”物理出口，避免拓扑变化时出现不确定行为。所选接口不可用时必须拒绝启动或停止恢复，不能静默改走另一张网卡。

### 3.2 使用强类型内部模型

节点数据不再用通用 `Username/Password/Method` 表达所有协议。建议节点存储 Schema 3 使用以下结构方向：

```go
type Input struct {
    ID              string
    Name            string
    Type            string
    Server          string
    Port            uint16
    Egress          string
    Authentication  AuthenticationInput
    TLS             *TLSInput
    Transport       *TransportInput
    ClearSecret     bool
}

type AuthenticationInput struct {
    Username string
    Password string
    UUID     string
    Method   string
    Flow     string
}
```

实际实现可根据 Go JSON 绑定需要拆分公开输入、公开节点和内部存储类型，但必须满足：

- 前端 RPC 永远不返回密码、UUID 等完整敏感字段。
- 协议特有字段有明确类型、白名单和长度限制。
- TLS、transport 使用结构化子对象，不保存自由格式 JSON。
- 订阅解析结果和手工输入进入同一规范化、校验与存储流程。

### 3.3 协议支持矩阵

| 协议 | 第一批字段 | TLS | Transport | 测试要求 |
|---|---|---|---|---|
| HTTP | username、password | 否 | TCP | HTTP CONNECT |
| Shadowsocks | method、password | 否 | TCP | 完整 SS 代理请求 |
| VMess | UUID、security | 可选 | TCP、WebSocket | 完整协议请求 |
| VLESS | UUID、flow | 可选 | TCP、WebSocket | 完整协议请求 |
| Trojan | password | 必需 | TCP、WebSocket | 完整协议请求 |

首期 VMess/VLESS/Trojan 不支持 gRPC、HTTPUpgrade、QUIC 和 Reality。字段存在但当前不支持时应明确拒绝，不能忽略后继续导入。

### 3.4 复用 sing-box 协议实现

不得自行实现 VMess、VLESS、Trojan 或 Shadowsocks 加密协议。节点测试和正式代理均复用锁定的 sing-box 核心。

正式代理继续走现有候选配置、`sing-box check`、helper 原子应用链路。协议级测速优先采用受限的短生命周期 sing-box 测试配置；测试配置只包含本地测试入口、单个被测 outbound、endpoint 防环路和固定测试目标，不接受订阅提供的命令、文件路径或任意配置片段。

## 4. 数据模型与迁移

### 4.1 节点 Schema 3

将 `internal/nodes.SchemaVersion` 从 2 升级到 3。迁移必须原子完成，并保留：

- 节点 ID、名称、服务器、端口和解析 IP。
- 当前所选节点。
- 收藏状态和订阅归属。
- 已加密的旧密码。
- HTTP 用户名。
- Shadowsocks 原 `Username` 字段中的 method。

旧节点迁移规则：

- `http`：迁移到 HTTP authentication，`egress = b`。
- `shadowsocks`：旧 `Username` 迁移为 `method`，`egress = b`。
- 不重新解密再加密原有密码，尽量直接保留 DPAPI ciphertext。
- 迁移校验或文件替换失败时不得覆盖 Schema 2 文件。

### 4.2 敏感字段存储

建议将所有协议密钥序列化为一个小型内部 secret document，再整体 DPAPI 加密，例如：

```json
{
  "password": "...",
  "uuid": "..."
}
```

公开节点只返回布尔能力信息，例如 `has_secret`、`has_uuid`，不得返回密钥摘要。TLS server name、transport path、flow 等是否视为敏感信息应在诊断脱敏测试中明确；默认诊断不记录完整 server、UUID、密码、订阅 URL、WebSocket path 或 Host header。

### 4.3 稳定节点身份

订阅刷新必须保留收藏和当前选择。节点身份不能继续只使用 `type|server|port`，否则同一服务器上的多个 UUID 节点会冲突。

建议对以下规范化字段生成带本地随机盐的 HMAC-SHA256 身份键：

```text
type + server + port + protocol identity + tls server name + transport + path
```

其中 protocol identity 可包含 UUID 或 password，但不得将原文或普通 SHA-256 写入日志、RPC 或诊断包。若暂不引入 HMAC，可在内存中比较解密后的结构，但不能持久化可离线猜测的普通密码哈希。

## 5. 配置生成与校验

### 5.1 扩展配置类型

扩展以下结构：

- `internal/config.MVPProxy`
- `internal/config.Outbound`
- `internal/config.TLSConfig`
- 新增 `TransportConfig` 及协议需要的字段。

建议 `MVPProxy` 仍是后端内部生成的强类型中间模型。前端传入的占位 `proxy` 不作为可信配置来源；`App.withSelectedProxy` 负责从节点存储构造完整代理配置。

### 5.2 防环路规则改造

当前固定规则为代理 endpoint `/32 -> foreign-direct`。改造后：

- `egress = a`：endpoint 路由到 `domestic-direct`。
- `egress = b`：endpoint 路由到 `foreign-direct`。
- 代理 outbound 的 `bind_interface` 必须与 endpoint direct outbound 对应。
- 域名节点解析必须从所选物理出口的源地址发起。
- DNS bootstrap 自身也必须通过对应物理出口。
- 语义校验必须验证 endpoint 规则、bind interface 和节点 egress 三者一致。

IPv6 节点 endpoint 暂不进入首期。节点服务器仍解析并固定为可用 IPv4；后续支持 IPv6 时应同时增加 `/128` 防环路规则和源接口 IPv6 解析约束。

### 5.3 四层校验

每种协议均必须通过：

1. 模型校验：协议字段组合、UUID、端口、TLS、transport、egress。
2. 生成 JSON Schema 校验：拒绝未知或缺失结构。
3. 语义校验：outbound 完整性、tag 引用、物理出口与防环路一致。
4. 锁定核心校验：使用 sing-box 1.13.15 执行 `check`。

协议字段应按当前锁定核心的实际配置格式实现，不能依据其他 sing-box 版本或 Xray 配置格式推断。

### 5.4 应用和回滚

节点切换流程：

1. 保存用户选择，但运行中的核心不立即无验证切换。
2. 解析节点域名并固定 endpoint IP。
3. 执行协议级健康检查。
4. 生成完整候选配置并完成四层校验。
5. 通过现有 helper/controller 原子应用候选配置。
6. 应用失败时保留或恢复最后成功配置，不回退为物理直连。

需要在实现时明确 UI 语义：若核心正在运行，可采用“验证后立即切换”或“停止后才能切换”。第一版建议继续禁止运行中切换，以降低连接中断、回滚和并发状态复杂度。

## 6. 订阅解析

### 6.1 支持顺序

按以下顺序实施：

1. 保留版本化 JSON 和现有 `ss://`。
2. 增加未编码及 Base64 多行分享链接。
3. 增加 `vmess://`、`vless://`、`trojan://`。
4. 增加 Clash/Mihomo YAML 受限子集。

解析器建议拆分为：

```text
internal/subscriptions/
  parse.go
  parse_json.go
  parse_links.go
  parse_vmess.go
  parse_vless.go
  parse_trojan.go
  parse_clash.go
  normalize.go
```

### 6.2 格式探测

格式探测不得仅凭首字符决定。建议顺序为：

1. 严格版本化 JSON。
2. 明文分享链接列表。
3. 整体 Base64 解码后再次识别分享链接列表。
4. YAML 受限文档。

每个解析器必须返回“格式不匹配”或“已匹配但内容非法”两类错误。格式已经匹配后不得继续尝试其他解析器，以免恶意输入绕过严格校验。

### 6.3 安全边界

继续保留并补强：

- 公网 URL 仅允许 HTTPS；HTTP 仅允许字面量私网或回环 IP。
- 禁止 URL userinfo 和重定向。
- 响应上限建议保持 1 MiB，只有真实订阅样本证明不足时才提高到 2 MiB。
- 节点上限保持 500。
- 设置总解析时间和单节点字段长度限制。
- YAML 禁用自定义 tag、anchor/alias 膨胀以及任意类型反序列化。
- 不读取订阅中的本地文件、provider、脚本、命令、插件或外部引用。
- 未支持的协议和字段明确报告，不静默降级。
- 更新必须先完成整批解析和校验，再原子替换；失败保留上一批节点。

Clash/Mihomo 首期只读取顶层 `proxies` 中已支持协议的必要字段，忽略整个文档中的代理组、规则、DNS 和 provider 是不安全的；应当明确拒绝这些字段或明确只选择 `proxies` 后记录“配置其他部分未导入”的结构化结果。用户界面需要展示成功、跳过和拒绝的节点数量及原因。

## 7. 连通性与延迟测试

### 7.1 测试分层

新的测试结果建议包含：

```go
type TestResult struct {
    NodeID            string
    Available         bool
    TCPReachable      bool
    ProtocolAvailable bool
    TCPMS             int64
    ProtocolMS        int64
    TotalMS           int64
    HTTPStatus        int
    ErrorCategory     string
    Error             string
    TestedAt          time.Time
}
```

测试阶段：

1. 使用节点选择的物理出口解析服务器域名。
2. 测试服务器 TCP 可达性，仅作为诊断数据。
3. 使用完整协议通过代理连接固定 HTTPS 测试目标。
4. 验证 TLS/HTTP 响应后才标记 `Available = true`。

TCP 可达不能显示为“节点可用”。

### 7.2 测试目标与隐私

测试目标应为应用内固定、可替换的 HTTPS 204 endpoint，并在文档中说明会产生外部请求。不要使用用户订阅提供的测试 URL。后续可提供自定义目标，但必须限制为 HTTPS、禁止凭据并防止访问本机和私网地址。

错误返回使用稳定分类，例如：

- `dns_failed`
- `egress_unavailable`
- `tcp_failed`
- `tls_failed`
- `authentication_failed`
- `protocol_failed`
- `target_failed`
- `timeout`
- `core_failed`

日志只记录节点 ID、协议、egress、阶段、耗时和错误分类，不记录凭据、完整服务器地址或 transport path。

### 7.3 批量测试

- 保留最多 4 个并发任务，但应允许取消并保证临时核心全部退出。
- 同一节点不得并发启动多个测试。
- 测试结果先保留在 UI 会话，不进入节点凭据文件。
- 批量测试失败不能修改当前所选节点。
- 排序时未测试节点应稳定排列，失败节点不应因为 `0 ms` 排到最前。

## 8. 后端和 RPC 改造

主要改动位置：

| 模块 | 改动 |
|---|---|
| `internal/nodes/model.go` | Schema 3、协议字段、egress、公开脱敏模型、测试结果 |
| `internal/nodes/store.go` | Schema 2 到 3 迁移、协议校验、secret document、稳定身份 |
| `internal/nodes/probe.go` | 分层测试接口；HTTP 快速路径和 sing-box 协议测试 |
| `internal/nodes/resolve.go` | 按 egress 选择源地址和 DNS 出口 |
| `internal/subscriptions/*` | 分享链接、Base64、多格式解析和规范化 |
| `internal/config/mvp_model.go` | 扩展代理中间模型 |
| `internal/config/minimal_tun.go` | 扩展 outbound、TLS、transport 类型 |
| `internal/config/mvp_generator.go` | 多协议生成、动态物理出口、防环路 |
| `internal/config/mvp_validate.go` | 协议与 egress 语义校验 |
| `docs/schema/winrouter-config-v1.schema.json` | 同步代理字段或评估升为配置 Schema 2 |
| `app.go` | 选中节点注入、动态接口解析、测试编排、错误脱敏 |
| `frontend/wailsjs` | Wails 绑定重新生成，不手工维护生成文件 |

配置 Schema 是否从 1 升到 2，应在第一阶段落地前决定。由于本次是向 `proxy` 增加字段且旧配置仍可表达，技术上可以兼容 Schema 1；但协议语义明显扩大，为避免旧程序误读新配置，建议升级为配置 Schema 2，并保留对 Schema 1 的显式迁移或拒绝说明。

## 9. 前端改造

代理页面建议保持单页工作流，但按功能分区：

1. 顶部：运行模式、所选代理节点和物理出口状态。
2. 节点工具栏：搜索、协议筛选、收藏筛选、排序、全部测试、添加节点。
3. 节点列表：名称、协议、endpoint、物理出口、TLS/transport 摘要、测试状态和选择操作。
4. 订阅区域：订阅元数据、更新时间、成功/跳过/失败数量、更新操作。

节点表单应根据协议动态显示字段：

- 协议使用 select。
- 物理出口使用 A/B segmented control，并显示真实接口名称。
- TLS 使用 toggle；启用后显示 server name 等字段。
- transport 使用 select；仅展示当前支持的选项。
- 密码和 UUID 使用 password 输入，并支持编辑时“留空保留”和“清除”。
- Shadowsocks method 使用白名单 select。

禁止把协议 URI 或 JSON 作为唯一手工录入方式。可另设“导入分享链接”对话框，先解析预览，再由用户确认保存。

运行中选择节点、删除当前节点、订阅刷新替换当前节点等场景必须有明确禁用或确认行为。任何情况下都不能在失败时显示已切换成功。

- 分享链接标准形式、URL 编码、Base64 padding、IPv4/域名和非法参数。
- 订阅超限、未知协议、尾随数据、混合合法/非法节点和原子回滚。
- egress A/B 对应 bind interface、DNS 源接口和 endpoint 路由。
- 节点身份冲突与订阅刷新保留收藏、选择。

### 11.2 集成测试

- 每种协议生成配置通过锁定 sing-box `check`。
- 临时测试核心正常退出、超时退出、取消退出和异常退出。
- 模拟 TCP 可达但协议认证失败。
- 域名节点解析成功后才提交新 IP，失败保留旧 IP。
- 核心应用失败时保留最后成功配置。
- helper 仍只接受限定操作，不开放任意命令或任意路径。

### 11.3 前端测试

- Vue 类型检查和生产构建。
- 每种协议表单字段、必填项和编辑保密语义。
- 切换协议时清除不再适用的秘密字段，避免隐藏字段误提交。

- 测试中、成功、失败、取消、未测试及订阅刷新状态。
- 运行中禁止危险切换，错误后不显示成功状态。

### 11.4 Windows 实机验收

每种协议至少验证：

1. 代理业务流量进入所选节点。
2. 代理服务器连接从所选 A/B 物理接口发出。
3. endpoint 不再次进入代理，不产生递归连接。
4. DNS bootstrap 从同一物理出口发出。
5. 节点断开、认证失败、DNS 变化时不回退直连。
6. 停止、崩溃、休眠、网络切换后无 sing-box/helper/TUN 残留。

## 12. 安全与发布门槛

发布前必须满足：

- 前端 RPC、日志、诊断包不包含密码、UUID、订阅完整 URL、WebSocket path 或敏感 header。
- 订阅输入不能触发命令执行、任意文件读取、外部 provider 加载或任意 sing-box 配置注入。
- 所有代理 endpoint 均有与物理出口一致的防环路规则。
- 所选物理出口不可用或代理失败时安全失败，不静默直连。
- 临时测速核心受版本、哈希、配置模板、超时和进程清理约束。
- 新增 YAML 依赖完成许可证和供应链检查。
- 实机抓包覆盖 A/B、DNS、TCP，并按协议补充 UDP 场景。
- 现有直连模式、规则系统、恢复、DNS 和 IPv6 全量回归通过。

## 15. 完成定义

本优化只有在以下条件全部满足时才视为完成：

- 用户可手工管理并选择 HTTP、SS、VMess、VLESS、Trojan 节点。
- 用户可明确选择代理服务器的物理出口 A/B。
- 分享链接订阅可安全解析、原子刷新并保留节点状态。
- UI 的“可用”来自完整协议请求，而不是 TCP 建连。
- 配置通过四层校验，代理 endpoint 不发生环路。
- 代理故障不会产生未授权直连回退。
- 密钥、订阅和诊断脱敏通过自动化及人工检查。
- 每种协议完成真实网络抓包和稳定性验收。
- 现有双出口直连和规则功能无行为回归。
